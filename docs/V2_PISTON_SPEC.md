# ドッキング履歴とピストン輸送（PT-1〜PT-4）

**Status:** PT-1・PT-2 DONE（2026-09-28）。PT-3 は実機確認待ち。PT-5 追加
**正本との関係:** `docs/ELITEINTEL_INTEGRATION_PLAN.md` §R.13 の統制手順に従う。全体テストの判定は「失敗 0 件」。

## 0. 目的と決定事項（2026-09-28）

- 交易で重要なのは、同じ 2 つのステーションを往復する「ピストン輸送」。前回のステーションへ、すぐ航路を設定してターゲットできるようにする。
- **ドッキング履歴は常に記録する**（ピストン輸送に限らず使う）。
- **荷物の売り買い（市場の操作）は自動化しない**（2026-09-28 TP 決定）。売り買いはプレイヤーが手で行う。
- 人が操作しない状態で航路設定・ドッキング・売買まで回し続ける仕組みは作らない（ゲームの利用規約の「ボット」に当たるおそれがあるため）。各動作は声・ボタンの指示、またはプレイヤーの操作（出航）をきっかけに 1 回ずつ動く。

## 1. PT-1: ドッキング履歴の記録

- 現状: `DockedStationRecord` は「今いるステーション」の情報を場所の記録に書くが、どの順にどこへドッキングしたかの履歴は無い。
- ドッキングのたび（Journal の `Docked`）に 1 件追加して DB に保存する（新規テーブル、マイグレーションは既存の最終番号の次。2026-09-28 時点で `01051`）。
  - 項目: ステーション名、星系名、`SystemAddress`、`MarketID`、ステーションの種類、恒星からの距離（Ls）、ドッキング日時
- `Location`（ドッキングしたままゲームを再開した場合）は、直前の履歴と同じ `MarketID` なら追加しない。
- 直前と同じ `MarketID` に続けてドッキングした場合（出てすぐ戻った等）は、新しい行を足さず日時だけ更新する。
- 保持は直近 50 件（定数）。超えたら古い順に削除。
- フリートキャリア（種類 `FleetCarrier`）も記録する。ただし位置が変わるため、PT-2 以降で使うときは別途現在地を確かめる。
- 読み出し: 「n 件前のステーション」（今いるステーションを 0 件前とする）、「直近の別々の 2 ステーション」（ピストンの両端）。
- 過去の Journal からの取り込みは今回行わない（必要なら別途）。
- PLAN CHECK で確定（2026-09-28）:
  - テーブル `docking_history`（マイグレーション `01051__docking_history.sql`）。列: `id`（INTEGER PRIMARY KEY AUTOINCREMENT）、`stationName`、`starSystem`、`systemAddress`、`marketId`、`stationType`、`distFromStarLS`、`dockedAt`（Journal の timestamp の ISO-8601 文字列）。並び順は `id`。
  - 新規 `DockingHistoryDao`／`DockingHistoryManager`（`QueryResultDisplayDao`／`QueryResultDisplayManager` に倣う）。「直前の行を見て追加／更新し、50 件を超えたら古い順に削除」は 1 回の呼び出しの中でまとめて行い、同時に呼ばれても崩れないようにする。
  - 直前と同じ `MarketID` のときは行を足さず、その行の全項目（日時・名前・種類・距離・星系・`SystemAddress`）を新しい値で更新する（キャリアは同じ `MarketID` のまま星系が変わるため）。
  - `MarketID` が 0（欠けている）のときは、ステーション名と `SystemAddress` の組で「同じステーション」を判定する。
  - ドッキング中の `Location` で直前と違う `MarketID` のときは、新しい行を 1 件足す（ツールを起動していない間の移動、撃墜後の再開など。今いる場所を 0 件前に保つため）。
  - 記録の呼び出しは `DockedSubscriber`／`LocationSubscriber` で行う。`LocationSubscriber` では EDSM への問い合わせより前に記録する（通信の待ち時間で順序が崩れないように）。
  - 起動時に読み返す古い Journal のイベント（replay／期限切れ）は既存の `JournalParser` が流さないため、重複の心配はない。
  - 読み出し: `getNthPreviousStation(back)`（0 = 最新、負や範囲外は空）、`getRecentDistinctStations()`（最新と、それと違う `MarketID` の直近 1 件。無ければ空）、`getHistory(limit)`。`DockingHistoryEntry.isFleetCarrier()`（種類 `FleetCarrier`）。

## 2. PT-2: 「前のステーションへ」

- 新規コマンド（例 `navigate_to_previous_station`）。引数 `back`（number、省略時 1。「2 つ前」なら 2）。
- 動作:
  - 対象のステーションを PT-1 の履歴から決める。ドッキング中なら今のステーションを 0 件前、ドッキングしていなければ直近のステーションを 0 件前とみなす（PLAN CHECK で扱いを確定）。
  - 対象が別の星系なら、既存 `RoutePlotter.plotRouteAnd` でその星系へ航路を設定する（P8-3 と同じ）。同じ星系なら航路は設定しない。
  - 既存 `ReminderManager.setReminder` で到着時の案内（ステーション名・星系名）を残す。
  - 答え: 「前のステーション、〇〇（△△ 星系）へ航路を設定します。」／同じ星系なら「前のステーションは同じ星系の 〇〇 です。」
  - 対象がフリートキャリアの場合、記録の星系と今の位置が違う可能性を伝える（現在地が分かる仕組みがあればそれを使う。PLAN CHECK で確認）。
  - 履歴が足りない場合は航路を設定せず断る。
- 本船外の判定は P8-3（`navigate_to_search_result`）と同じ（`isVisibleForLLM` は常に true、`execute` 内で断る）。GUI から呼ぶ場合の読み上げも P8-3 と同じ方式。
- EN/JA エイリアス: 例「前のステーションへ」「前のステーションに戻って」「さっきのステーションへ」「2 つ前のステーションへ」「ピストン先へ」。
- H-1（ゲームを前面にしてからキーを送る）の対象コマンド（キーを送る）として扱う。
- PLAN CHECK で確定（2026-09-28）:
  - コマンド `navigate_to_previous_station`、新規 `NavigateToPreviousStationCommand`（`NavigateToSearchResultCommand` と同じく、航路設定・本船判定などを差し替えられる形にしてテストする）。
  - `back` は省略時 1。1 未満や小数は断る。履歴の件数を超えるときは「履歴不足」で断る。
  - 数え方: 基本は「履歴の `back` 件目（最新を 0 件目）」。例: A→B とドッキングして B にいる／B から出航した後、どちらも back=1 は A。
    - ただし**ドッキング中で、最新の履歴が今いるステーションと一致しないとき**（履歴が取れていない等）は、今いるステーションは履歴に無いものとして `back - 1` 件目を使う。
  - 同じ星系かどうかは、今いる星系の `SystemAddress` と履歴の `systemAddress` で比べる（取れないときだけ星系名で比べる）。
  - 同じ星系でも `ReminderManager` に星系名・ステーション名を残す（HUD の目標表示のため）。航路は設定しない。
  - フリートキャリア: 自分のキャリア（コールサインがステーション名と一致）なら `PlayerSession.getCurrentFleetCarrierSystem()` の星系へ航路を設定し、記録の星系と違えばその旨を伝える。他人のキャリアは記録の星系へ航路を設定し「移動している可能性があります」と添える。
  - 答えの文言（JA）: 別の星系「前のステーション、{0}（{1} 星系）へ航路を設定します。」、同じ星系「前のステーションは同じ星系の {0} です。」
  - 日本語のエイリアスは、音声認識で数字が漢数字・かなになる場合に備え「二つ前」「ふたつ前」も入れる。

## 3. PT-3: 到着後にステーションを自動でターゲットする

- 背景: Odyssey 以降、ステーションのブックマークから航路を引いても、到着時に目的地はステーションではなく星系（恒星）になる（Steam コミュニティの報告）。星系内のステーションはナビゲーションパネル（左パネル）で選ぶ必要がある。
- 仕組み（閉ループ）:
  1. 目的の星系に着いた（Journal の `FSDJump` が目的の星系）、または同じ星系で PT-2 を実行した時点で開始する。
  2. 左パネルを開き（`FocusLeftPanel`）、ナビゲーションのタブへ移る（`CycleNextPanel` 等）。
  3. 一覧の行を選んでターゲットする（`UI_Select` 等。押す回数は実機で確定）。
  4. `Status.json` の `Destination.Name` を読み、目的のステーション名と一致すれば終了（パネルを閉じる）。
  5. 一致しなければ 1 行下へ（`UI_Down`）移り、3〜4 を繰り返す。
  6. 上限（定数、初期値 30 行）までに見つからなければ中止し、「〇〇をターゲットできませんでした」と伝える。途中で状況が変わった（ドッキング、ジャンプ開始、パネルが開けない等）ときも中止する。
- 探し始める位置: ナビゲーションパネルの一覧は船から近い順。ジャンプ直後は恒星のそばにいるため、ステーションの「恒星からの距離」を手がかりに開始位置を推定してよい（PLAN CHECK で判断）。
- 1 回ごとに `Status.json` の更新を待つ（上限時間は定数）。
- **実機での確認が必要な点**（PT-3 の実装前に、TP が手で確かめる手順を PLAN CHECK で用意する）:
  - 左パネルを開いたとき、最初にどのタブが表示されるか。確実にナビゲーションのタブへ移る手順
  - 一覧で `UI_Select` を押したとき、すぐターゲットされるか、小さなメニュー（ターゲット／情報など）が出るか
  - 1 行下へ移るキーと、パネルを閉じるキー
  - `Destination.Name` にステーション名がどう入るか（表示言語による違い、キャリアの場合など）
- PT-3 は、PT-2 の後に別サブフェーズとして実機で調整しながら進める。

## 4. PT-4: ピストンモード（任意）

- 「ピストン輸送開始」「ピストン輸送終了」で切り替える。モード中は両端 A・B を保存する（アプリを再起動しても残す）。
- **両端の決め方は 2 通り**（2026-09-28 TP 追加）:
  1. **ドッキング履歴から**: 「ピストン輸送開始」だけのとき。PT-1 の `getRecentDistinctStations()`（直近の別々の 2 ステーション）を A・B にする。
  2. **交易候補から**: 「交易候補 1 でピストン輸送」「ランク 2 でピストン」のように順位を付けたとき。直近に表示した交易候補（`QueryResultDisplayManager` の `trade_candidates`、P8）のその順位の**購入地を A、売却地を B** にする。
     - 最後の表示が交易候補でない（艤装の検索結果など）、または順位が範囲外なら断る（P8-3 `navigate_to_search_result` と同じ扱い）。
     - 開始時点で A にドッキングしていなければ、まず A（購入地）へ航路を設定する（P8-3 の購入地への案内と同じ）。すでに A にいればそのまま待つ。B にいる場合は A へ航路を設定する。
     - 交易候補には `MarketID` が無いため、A・B とドッキング先が同じかどうかは**ステーション名と星系名（大文字小文字を区別しない）**で判定する。
- モード中、A または B から出航（Journal の `Undocked`）したら、もう一方への航路（PT-2 と同じ扱い）と、到着後のターゲット（PT-3。実装済みの場合）を自動で行う。
- A・B 以外のステーションにドッキングしたら、モードを自動で終了して伝える。
- 開始・終了・出航時の案内は声で伝える（例: 「ピストン輸送を開始します。購入地 〇〇（△△ 星系）と売却地 □□（◇◇ 星系）の間を案内します。」「売却地 □□ へ航路を設定します。」）。HUD／AI タブにモード中であることと A・B を表示するかは PLAN CHECK で決める。
- 売り買いは行わない（§0）。航路の設定・ターゲットはプレイヤーの出航をきっかけに 1 回ずつ動き、人が操作しない連続運転にはしない（§0）。
- PLAN CHECK で確定（2026-09-28。実装は PT-5 のマージ後）:
  - `start_piston_mode`（引数 `rank` 省略可）／`stop_piston_mode`。状態は新規テーブル `piston_mode`（1 行、マイグレーション `app/src/main/resources/db-migration/01052__piston_mode.sql`）に保存。
  - 履歴から開始したとき: 最新の履歴を X、それと違う直近を Y とする。X にドッキング中ならそのまま待つ。ドッキングしていなければ（X から出航済み）Y へ航路を設定する。
  - **出航時の航路設定のタイミング**: `Undocked` の直後はオートローンチ中でステーション内にいるため、すぐにはキーを送らない。一定時間（定数、初期値 15 秒。実機で調整）待ってから、本船・未ドッキング・パネルやマップを開いていない（GuiFocus なし）・ゲームが前面、をすべて満たすときだけ航路を設定する。満たさないときは航路を設定せず「〇〇へは『前のステーションへ』で航路を設定できます」と声で伝える（ゲームを勝手に前面にはしない）。
  - エイリアス: 「ピストン輸送開始」等に加え、交易候補からの開始「交易候補 {rank:X} でピストン輸送」「ランク {rank:X} でピストン輸送」「{rank:X} 位でピストン輸送」（EN も同様）。PT-2 の「ピストン先へ」は残す。
  - HUD／AI タブの表示は今回は行わない（声の案内のみ）。表示は別途。
- **エイリアスの注意**: PT-2 の「ピストン先へ」と、PT-4 の「ピストン輸送開始」「交易候補 1 でピストン輸送」が取り違えられないこと。PT-4 の PLAN CHECK で、PT-2 側の「ピストン先へ」を残すか外すかも含めて決め、衝突テストと埋め込みルーティングテストで確かめる。

## 4.5 PT-5: 声で自動ドッキング（ドッキング要求 → 許可 → スロットル 0）

- 背景（2026-09-28 TP 決定、案 1）: ドッキングコンピューターによる自動ドッキングは「ステーションから 7.5 km 以内・ドッキング許可が下りている・スロットル 0」の 3 つがそろうと始まる（Elite Dangerous Wiki「Advanced Docking Computer」）。いまは「ドッキングを要求」（`request_docking`）と「オートドッキング」（`taxi_to_landing_pad`。中身はスロットル 0 のキー 1 回）が別々で、許可を待ってから 0 にする操作をプレイヤーが 2 回言う必要がある。
- 新規コマンド（例 `auto_dock`）。1 回の指示で次を行う:
  1. 既存 `RequestDockingCommand` と同じ手順でドッキングを要求する（手順は共通化して重複させない。PLAN CHECK で方法を決める）。
  2. Journal の `DockingGranted` を待つ（上限時間は定数、初期値 20 秒）。
  3. 許可が下りたらスロットル 0（`SET_SPEED_ZERO`）を 1 回送る。案内は既存の管制の読み上げ（パッド番号）に続けて「スロットルを 0 にしました。自動ドッキングを開始します。」
  4. `DockingDenied`（拒否。理由付き）なら、スロットルは変えずに理由を伝える（例: 距離が遠い、敵対、満杯）。`DockingTimeout`／`DockingCancelled` や上限時間切れも、スロットルは変えずに伝える。
  5. すでに同じステーションの許可が下りている（直前の `DockingGranted` が有効）なら、要求は送らずスロットル 0 だけ行う。
- 使える状況: 本船・通常空間・ドッキングしていない・スーパークルーズ中でない（`taxi_to_landing_pad` と同じ）。それ以外は断る。
- ドッキングコンピューターの有無: 船の装備（Loadout）から分かるなら、積んでいないときは要求だけ行い「ドッキングコンピューターが無いため、手動で着艦してください」と伝える（スロットルは変えない）。装備が分からないときは通常どおり行う。既存の装備の記録の有無は PLAN CHECK で調べる。
- `DockingDenied`／`DockingTimeout`／`DockingCancelled` のイベントがアプリに無ければ追加する（既存の `DockingGrantedEvent` に倣う）。
- 1 回の声の指示で 1 回だけ動く。自動で繰り返し要求しない（§0）。
- H-1（ゲームを前面にしてからキーを送る）の対象。
- エイリアス: 「オートドッキング」「自動ドッキング」を `taxi_to_landing_pad` から新コマンドへ移す。追加案「ドッキングして」「自動で着艦」「着艦して」「auto dock」「dock the ship」。`taxi_to_landing_pad` は「ドッキングコンピューター起動」「タクシー」等を残す。`request_docking` の「ステーションにドッキング」をどちらに置くかは PLAN CHECK で決め、衝突テストと埋め込みルーティングテストで確かめる。
- PT-4（ピストンモード）とは独立。後で PT-4 の到着後の流れに組み込むかは別途決める。
- PLAN CHECK で確定（2026-09-28）:
  - `AutoDockCommand`（`auto_dock`）。要求の手順は `RequestDockingCommand` から共通メソッドに切り出して両方から呼ぶ（既存の動作は変えない）。
  - **`execute` は許可を待たずにすぐ返す**（「ドッキングを要求しました。許可が下りたらスロットルを 0 にします。」）。待つ処理は別の仮想スレッドで行い、結果（スロットル 0／拒否理由／時間切れ／取消）は声（`AiVoxResponseEvent`）で伝える。VEGA の 1 回の応答を 20 秒止めないため。
  - 許可・拒否・時間切れ・取消のイベントを待つ受け口は、**要求のキーを送る前に**用意する（許可が先に届いて取りこぼすのを防ぐ）。
  - `DockingDeniedEvent`／`DockingTimeoutEvent`／`DockingCancelledEvent` を追加し `EventRegistry` に登録。許可の状態は新規 `DockingStateTracker`（`DockingGranted` で有効、`Docked`／拒否／時間切れ／取消／`SupercruiseEntry`／`FSDJump`／`Undocked` で無効、10 分で失効）。
  - ドッキングコンピューターの有無は `ShipLoadoutManager` の装備（`int_dockingcomputer_*`）で判定。装備情報があり、積んでいない（または電源オフ）と確実に分かるときだけ要求のみにする。
  - 文言のキーは既存に合わせ `handler.autoDock.*`。拒否理由（Distance／NoSpace／Hostile／Offences／TooLarge／ActiveFighter／その他）ごとに JA/EN を用意。
  - エイリアス: 「オートドッキング」「自動ドッキング」「ドッキングして」「自動で着艦」「着艦して」「ステーションにドッキング」を `auto_dock` へ（「ステーションにドッキング」は `request_docking` から移す）。`taxi_to_landing_pad` に「ドッキングコンピューター起動」を追加。
