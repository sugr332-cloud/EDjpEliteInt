# 実機確認で出た修正（LF-1〜LF-6）

**Status:** Draft（2026-09-30）
**正本との関係:** `docs/ELITEINTEL_INTEGRATION_PLAN.md` §R.13 の統制手順に従う。全体テストの判定は「失敗 0 件」。
**背景:** 2026-09-29〜30 の実機確認（PT-1〜PT-5）で、ピストン輸送は動いた。一方で、質問に動作のコマンドが反応する、キー設定の重なりで思わぬ操作が起きる、などが見つかった。

## LF-1: 質問と動作を分ける／「前のステーション」の意味をそろえる

- 実機（2026-09-30）: 「前のステーションはどこ？」で `start_piston_mode` が動き、「前のステーションを教えて」で `navigate_to_previous_station` が動いた。聞いているだけなのに航路設定やピストン輸送が始まる。
- 「前のステーション」の意味（2026-09-30 TP 決定）: **前回着艦していたステーション**。
  - ドッキング中: 今いるステーションの 1 つ前（履歴の 1 件目。PT-2 の例外規則（今いるステーションが履歴に無い場合）はそのまま）。
  - ドッキングしていない: 最後に着艦していたステーション（履歴の 0 件目）。
  - PT-2（`navigate_to_previous_station`）の数え方もこれに合わせる（未ドッキング時の back=1 は 0 件目、back=2 は 1 件目）。ピストンモード（PT-4）は両端を自分で持つので影響しない。
- 新規クエリ（航路を設定しない、答えるだけ）:
  - `query_previous_station`: 上の意味の「前のステーション」を、ステーション名・星系名・種類・恒星からの距離で答える。履歴が無ければ「記録がありません」。
  - `query_current_station`: ドッキング中ならそのステーション、していなければ「ドッキングしていません。最後に着艦したのは〇〇です」。
- エイリアスの整理:
  - 動作のコマンドから、動詞の無い短い言い方を外す: `navigate_to_previous_station` の「前のステーション」「previous station」、`start_piston_mode` の「ピストン輸送」「ピストンモード」「piston mode」「piston trade」。
  - 動作のコマンドは「〜へ」「〜に戻って」「〜へ航路」「〜開始」「〜を始めて」など動作を表す言い方だけにする。
  - 質問の言い方（「前のステーションはどこ」「前のステーションを教えて」「さっきどこにいた」「今いるステーションは」「今どこにドッキングしている」など）はクエリへ。
  - 埋め込みルーティングテストで、質問はクエリが、動作はコマンドが上位になることを確かめる。

## LF-2: キー設定を声で答える

- TP 要望（2026-09-30）: 「何が何のキーに設定されているか」を聞かれたら答える。
- 新規クエリ `query_key_binding`（答えるだけ、キーは送らない）:
  - 操作名から: 「ジャンプのキーは？」「サイレントランニングは何のキー？」→ その操作のキーボード・その他の機器の割り当て（主・副）。
  - キーから: 「J キーは何？」「左 Ctrl に何が割り当てられている？」→ そのキー（組み合わせ）に割り当てられている操作。
  - 重なり: 「キーの重なりを教えて」→ 既存 `BindingConflictScanner` の結果（LF-3 の単独修飾キーを含む）。
- 実装の方針: 既存の `KeyBindingsParser`／`BindingsMonitor` が読んでいる .binds を使う。操作名の照合は既存 `BindingDisplayNames`（`/bindings/ed_control_names.properties`）の表示名と検索用テキストを使い、キーの読み上げは既存 `BindingChordSpeech` を使う。日本語での言い換えは LLM に任せ、データ（操作 ID・表示名・キー）を正確に渡す。
- 候補が複数あるときは上位数件を返し、LLM が確認する。

## LF-3: 修飾キー単独の割り当てを警告する

- 実機: 左 Ctrl 単独が「ルートの次の星系を選択」「後退 25%」「シールドセル使用」、右 Shift 単独が「サイレントランニング（押すたびに切替）」、左 Shift 単独が「減速 50%」「UI フォーカス」「アドバンスモード」に割り当てられていた。アプリが Ctrl／Shift を含む組み合わせを送ると、修飾キーを押した瞬間にそれ単独の操作が動く（後退、サイレントランニングで温度上昇）。
- 既存 `BindingConflictScanner` は「同じキーの組み合わせ同士」だけを重なりとみなすため、この種類を見つけられない（同じ単独修飾キーに複数の操作が付いた場合だけは見つかるが、「単独修飾キー」と「その修飾キーを含む組み合わせ」の関係は見ない）。
- 追加: 宇宙船の場面（既存 `BindingConflictRules` の場面の区別に従う）で、Ctrl／Shift／Alt が**単独**で操作に割り当てられていて、かつ同じ修飾キーを含む組み合わせがアプリの送る操作にある場合、起動時に警告する（既存の起動時警告 `KeyBindCheck` の流れに足す）。どの操作とどの操作が関係するかをログと声で伝える。
- 声の警告は既存の「重大な重なり」と同じ扱い（起動のたび）にするかは PLAN CHECK で決める。

## LF-4: 自動ドッキングでスロットルレバーを知らせる

- 実機: スロットルに X52 の軸（`ThrottleAxis`、デッドゾーン 0）が割り当てられていると、キーで速度 0 にしてもレバーの位置に戻され、自動ドッキングに入らない。アプリからレバーは動かせない。
- `auto_dock`（PT-5）で許可が下りたとき、.binds の `ThrottleAxis` に機器が割り当てられていれば、スロットル 0 のキーを送ったうえで「スロットルレバーを 0 にしてください」と声で伝える（`handler.autoDock.throttleAxis`）。割り当てが無ければ従来どおり。

## LF-5: ジャンプのキーの代わり

- 実機: TP は普段「ハイパー／スーパー切り替え」（`HyperSuperCombination`、J）でジャンプしている。アプリの `jump_to_hyperspace` は「ハイパースペースジャンプ」（`Hyperspace`）だけを押す。
- `Hyperspace` にキーボードの割り当てが無いときは、通常空間でルートの次の星系がターゲットされている場合に限り `HyperSuperCombination` を押す（通常空間でターゲットがあると、切り替えキーはハイパースペースジャンプになる）。どちらも無ければ「ジャンプのキーが設定されていません」と答える。
- `Hyperspace` が割り当て済みで効かない場合の扱い（LF-3 の単独修飾キーが原因だった可能性）は、TP のキー設定修正後の実機結果を見てから決める。

## LF-6: 意味の無い発話を AI に送らない

- 実機: 「ああ」「ハハハ」「はい」「うるせえ」などが AI に送られていた（P5-4 の相づちの捨て方では拾い切れていない）。
- 捨てる対象を広げる: 笑い声・感嘆だけの発話（例「ああ」「あー」「ハハハ」「ははは」「ふふ」「へえ」「ほう」「おお」）。**「はい」「いいえ」は捨てない**（危険な操作の確認の返事に使うため）。
- 対象の一覧と判定の場所は PLAN CHECK で決める（既存 `ParakeetSTTImpl` の日本語の相づち判定に足す想定）。捨てたものはログに `STT: dropped` として残す。
