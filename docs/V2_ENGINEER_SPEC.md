# エンジニア（開放条件・場所・進み具合・案内）EG-0〜EG-4

**Status:** EG-0 DONE（2026-10-01）。EG-1〜EG-4 は PLAN CHECK 待ち
**正本との関係:** `docs/ELITEINTEL_INTEGRATION_PLAN.md` §R.13 の統制手順に従う。全体テストの判定は「失敗 0 件」。

## 0. 目的（2026-09-30 TP 要望）

- 「FSD の性能を上げるエンジニアは？」「〇〇（エンジニア）の開放条件は？」「エンジニアのステーションへ向かって」に答え、案内する。
- エンジニアについて聞かれたら、交易候補を表示している場所（AI タブのカード、P8 §7.1）に、エンジニアの名前とステーション（基地）を出す。
- カードにはチェックリストを付け、どこまで進んでいるか（知っている／招待済み／面識あり／開放済み／ランク）を確認できるようにする。
- カードに「ステーションへ発進」ボタン（そのエンジニアの星系へ航路を設定する）を付ける。声でも同じことができる（P8 §7.2 と同じ「声とクリックの両方、HUD はクリックしない」方針）。

## 1. データの出どころ

| 知りたいこと | ゲームの記録（Journal）で分かるか | どこから取るか |
|---|---|---|
| 各エンジニアの進み具合（知っている／招待済み／面識あり／開放済み／出入り禁止） | 分かる（`EngineerProgress` の `Progress`） | Journal |
| 開放済みエンジニアのランク（1〜5）と次のランクまでの進み（%） | 分かる（`Rank`、`RankProgress`） | Journal |
| エンジニアの場所（星系・基地名） | 分からない | アプリに持たせる固定データ（EG-0） |
| 招待の条件・開放の条件・紹介元 | 分からない | 固定データ（EG-0） |
| 得意分野（どのモジュールを何グレードまで改造できるか） | 分からない | 固定データ（EG-0） |
| 開放条件のうち、今どこまで満たしているか（例: 素材を何個納めたか） | ほぼ分からない | 手動のチェック（EG-3） |

- `EngineerProgress` は、ゲーム開始時に全エンジニアの一覧（`Engineers` 配列）として 1 回、進み具合が変わったときにそのエンジニア 1 人分（配列ではなく `Engineer`／`Progress` などが直下に並ぶ形）で書かれる。今のアプリの `EngineerProgressEvent` は配列の形しか読んでおらず、`EngineerProgressSubscriber` は何も保存していない（コメントのみ）。両方の形を読んで保存する必要がある（EG-1）。

## 2. EG-0: 固定データを作る（Claude 担当）

- 宇宙船のエンジニア（Horizons）と徒歩のエンジニア（Odyssey）について、次を 1 つの JSON（例: `app/src/main/resources/engineers/engineers.json`）にまとめる。
  - 名前、種類（ship／onfoot）、星系名、基地名、天体、星系の座標（距離の計算用）。Journal とは**名前（大文字小文字を区別しない）**でつなぐ（公開データに `EngineerID` の一覧が無いため。EG-1 で初めて見た `EngineerID` を名前と一緒に保存してよい）
  - 招待の条件、開放の条件、紹介元（どのエンジニアから紹介されるか）
  - 得意分野: 改造できるモジュールと最大グレード（例: Frame Shift Drive → 5）
  - 日本語で読むための表示名（モジュール名など）は、既存の日本語化の表と合わせる
- 出どころは、信頼できる公開データ（コミュニティの定番の資料）を Claude が調べて決め、JSON の先頭に出どころと確認日を書く。ゲームの更新でエンジニアが追加・移動することがあるため、確認日を残す。
- 出どころの候補（2026-09-30 時点。TP 確認済み: 場所・条件・得意分野は公開サイトで取れる）:
  - INARA のエンジニア一覧（https://inara.cz/elite/engineers/）
  - EDEngineer の同梱データ（GitHub msarilar/EDEngineer の `Resources/Data`。ブループリントとエンジニア、場所、開放条件を JSON で持つ）
  - Elite Dangerous Wiki（Fandom）のエンジニアのページ
- アプリの実行中にサイトから毎回取りに行く方式は取らない（INARA にはエンジニア情報を返す公開の API が無く、ページの読み取りは壊れやすく利用規約にも関わるため）。公開データから固定の JSON を作ってアプリに同梱し、ゲームの更新時に作り直す。EDEngineer のデータを元にする場合は、そのライセンスを確かめてから使う。
- この JSON は Claude が作成して docs と一緒に提出し、agy は EG-1 でそれを読み込む仕組みを作る。

## 3. EG-1: 進み具合を保存する

- `EngineerProgress` の 2 つの形（全員の一覧、1 人分の更新）を両方読み、エンジニアごとに「進み具合・ランク・ランクの進み・更新日時」を DB に保存する（新規テーブル）。
- アプリの起動前にゲームが書いた `EngineerProgress` も取り込めること（既存の起動時の読み込みの仕組みで届くかを PLAN CHECK で確かめる。届かなければ、最新の Journal から探して取り込む）。
- 固定データ（EG-0）とは名前でつなぐ（大文字小文字を区別しない。`Tod 'The Blaster' McQuinn` のような引用符の違いに注意）。

## 4. EG-2: 声で聞く（クエリ）

- 得意分野から探す: 「FSD の性能を上げるエンジニアは？」「シールドを改造できるエンジニア」→ そのモジュールを改造できるエンジニアを、最大グレードの高い順・今いる場所から近い順に。開放済みかどうかと今のランクも添える。
- エンジニアのことを聞く: 「フェリシティ・ファーシーアの開放条件は？」「〇〇はどこ？」→ 場所、招待・開放の条件、紹介元、今の進み具合。
- 進み具合の一覧: 「エンジニアの進み具合は？」「開放済みのエンジニアは？」
- 答えるときは EG-3 のカードも表示する。

## 5. EG-3: カード表示とチェックリスト

- 交易候補と同じ表示の仕組み（`QueryResultDisplayManager`、新しい種類 `engineers`）で、AI タブにエンジニアごとの枠を出す（P8 §7.1 と同じく、1 人ずつ別の枠、項目は段落で分ける）。
  - エンジニア名、種類（宇宙船／徒歩）、基地名、星系名、今いる場所からの距離
  - 得意分野（聞かれたモジュールがあれば、その最大グレードを目立たせる）
  - チェックリスト:
    - 自動で付くもの（Journal から）: 知っている → 招待済み → 面識あり → 開放済み → ランク 1〜5（今のランクと次までの %）
    - 手動で付けるもの: 招待の条件・開放の条件のうち Journal で分からない項目（例: 「素材を〇個納めた」）。チェックはプレイヤーがクリックして付け外しし、DB に保存する
  - 「ステーションへ発進」ボタン（EG-4）
- HUD には要約のみ（クリックしない）。

## 6. EG-4: エンジニアのステーションへ案内

- 新規コマンド（例 `navigate_to_engineer`）: 「〇〇のところへ向かって」「〇〇のステーションへ」「FSD のエンジニアへ向かって」（候補が複数なら、直前に表示したカードの 1 番目か、確認する）。
- 動作は P8-3（`navigate_to_search_result`）と PT-2 と同じ: 別の星系なら航路を設定し、リマインダーに星系名・基地名を残す。同じ星系なら航路は設定しない。本船外は断る。H-1 の対象。
- カードのボタンからも同じコマンドを呼ぶ（GUI から呼んだときの読み上げも P8-3 と同じ）。
- エンジニアの基地は多くが惑星の地上にあるため、到着後の案内（惑星への降下など）は今回は行わない。

## 7. 非目標

- 改造（ブループリント）の必要素材の計算
