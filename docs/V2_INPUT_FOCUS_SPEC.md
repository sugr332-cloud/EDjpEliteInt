# キー入力先の保護と FSD 表記（H-1 / J-19）

**Status:** Draft（2026-09-27）
**正本との関係:** `docs/ELITEINTEL_INTEGRATION_PLAN.md` §R.13 の統制手順に従う。

## 0. 背景（2026-09-27 実機）

- AI タブの入力欄に「マップ開いて」と打つと、ゲームのギャラクシーマップは開かず、アプリのチャット欄に「+」が入った。「ジャンプしろ」も、ジャンプ先と「FTLの準備中です」が表示されただけで、ゲームは動かなかった。
- 原因: キー入力は Windows の **前面のウィンドウ** に送られる（`WindowsNativeKeyInput`）。文字入力ではアプリが前面なので、ゲーム用のキー（ギャラクシーマップのキーなど）がアプリ自身の入力欄に入る。ゲームを前面に出す処理（`GameWindowActivator`）は GUI ボタン経由（`GuiCommandRunner`）でしか呼ばれていない。音声入力はゲームが前面のまま話すので、この問題が表に出なかった。
- 危険性: 前面がアプリ以外（ブラウザ・チャットツール等）の場合、ゲーム用のキーがそのアプリに打ち込まれる。
- 日本語の表記: `responses_ja` / `gui_ja` が英語版の「FTL」をそのまま使っている。Elite Dangerous の日本語話者の用語では、船の超光速航法は FSD（フレームシフトドライブ）で、スーパークルーズとハイパースペースジャンプの両方を FSD が行う。

## 1. H-1: キー入力の前にゲームを前面にする

- ゲームへキー入力を送る **共通の入口**（全コマンドが通る 1 か所。PLAN CHECK で特定する）で、送る直前に次を行う:
  1. 前面ウィンドウが Elite Dangerous なら、そのまま送る（従来どおり。音声入力の通常経路）
  2. そうでなければ Elite Dangerous のウィンドウを前面にする（既存 `GameWindowActivator` の処理を共通部品として使えるようにする。`GuiCommandRunner` の動作は変えない）。前面になったことを確認できるまで最大 2 秒待ち、その後、短い待ち（定数、初期値 300 ms）を置いてから送る
  3. ゲームのウィンドウが見つからない、または前面にできなかったときは **キーを送らない**。その操作は中止し、「ゲームのウィンドウを前面にできないため、操作を送りませんでした。」を読み上げる（EN も用意）。ほかのアプリにキーが入ることを防ぐ
- Windows 以外（Linux 等）は現状どおり（判定をしない）。
- 既知の制約: ゲームが前面に来たときに音声デバイスがリセットされ、直前に始まった読み上げが途切れることがある（`GuiCommandRunner` が 3 秒待つ理由）。H-1 では待ちは 300 ms とし、途切れが実機で問題になれば別途調整する。
- テスト: 前面判定・前面化・待ちを差し替え可能にし、(a) 既に前面なら前面化しない、(b) 前面でなければ前面化してから送る、(c) 見つからない／前面化に失敗したら送らず中止メッセージを出す、を検証する。実機のウィンドウ操作・キー送信はテストで行わない。

## 2. J-19: 日本語の「FTL」を「FSD」に

- `responses_ja.properties`: `handler.fsd.nodestination`、`handler.supercruise.massLocked`、`handler.supercruise.preparingFtl` の「FTL」を「FSD」に（例「FSDの準備中です。」「マスロック状態のため、FSDは使用できません。」「FSDの目的地が設定されていません。」）
- `gui_ja.properties`: `automation.*ForFtl` の 5 キーの「FTL移行時に」を「FSD起動時に」に
- キー名・英語版は変更しない。`ai_action_aliases_ja.properties` の「FTLをドロップ」は言い回しとして残してよい
